# ADR-0001 — System Boundaries and Ownership

**Status:** Accepted (Amended 2026-08-20 — Amendment 2)

**Purpose:** Define the architectural boundaries between GOS, guava-os, OMP,
GitHub, Linear, and project repositories. This document is the source of truth.
When code or documentation conflicts with this ADR, this ADR wins.

---

## Amendment 2 summary (2026-08-20)

Amendment 2 reorients the system around OMP's native orchestration and retires
gorp as a standalone execution engine. It supersedes every conflicting clause
in the original ADR and in Amendment 1.

- **gorp is retired.** Its enforcement mechanics (execution graph, transition
  table, hash-chained audit, fail-closed promotion, worker adapter, scheduler,
  git-worktree sandbox) are replaced by composed tools: OMP subagents for
  execution, GitHub branch protection + pull-request review + CI for
  authorization, and Linear for workflow state.
- **OMP is now the orchestration substrate**, not merely a runtime. guava-os
  drives OMP primitives (`task` subagents, DAG fan-out, isolated worktrees,
  process supervision) directly.
- **GitHub owns authorization.** Protected branches, required reviews, and
  required status checks are the machine enforcement of "workers never merge."
- **Linear is the workflow state of record.** An issue is the unit of work,
  the worker's task contract, and the handoff record. Commits carry the
  canonical `GUA-###` identifier.

---

# Why

The repository has accumulated overlapping responsibilities.

Planning, orchestration, execution, runtime, and governance became blurred,
and gorp grew a second, parallel enforcement layer (audit chain, transition
table, promotion gates) that duplicates what git, GitHub, and CI already
provide. This ADR removes that duplication and re-centers the system on
composed tools.

---

# Core Principle

Separate **thinking** from **execution**.

Planning is not execution.

Governance is not execution.

Authorization is a repository concern, not a runtime concern.

Execution does not own business decisions.

---

# System Overview

```
Operator
    │
    ▼
OMP Session (guava-os agent — the control plane)
    │  drives OMP primitives: task subagents, DAG fan-out,
    │  isolated worktrees, process supervision
    ▼
Workers (OMP subagents, one per Linear deliverable, isolated worktrees)
    │  commit with GUA-### identifier → push to dev/<role>
    ▼
GitHub (authorization: branch protection, PR review, required CI checks)
    │  dev/<role> → staging → production
    ▼
Project Repositories
    │
    ▼
Linear (canonical backlog + workflow state of record)
```

Knowledge compounds upward. Execution flows downward.

# Component Responsibilities

## GOS

GOS is the operating model. It defines how engineering work compounds across
projects. GOS is **not** a runtime.

### Owns

* operating model
* governance model
* capability model
* promotion model
* architectural principles

### Does NOT Own

* execution
* worker runtime
* planning implementation
* project management

---

## guava-os

guava-os is the control plane and the orchestrator. It understands projects,
plans work, decides what should happen next, and drives execution through
OMP's native primitives. It does not hand-build execution machinery.

### Owns

* project state
* planning
* task decomposition
* orchestration (driving OMP subagents and DAG fan-out)
* Linear integration
* governance workflow
* review workflow
* promotion workflow (dev → staging → production via GitHub)
* project registry
* cross-project awareness
* roles

### Does NOT Own

* authorization (GitHub owns this)
* worker runtime (OMP owns this)
* a custom execution engine (none exists; gorp is retired)
* audit integrity (git history + CI logs own this)

---

## OMP

OMP is the engineering runtime **and** the orchestration substrate.

### Owns

* runtime
* shell
* tools
* context loading
* memory
* skills loading
* model access
* subagent dispatch (`task`, `eval agent()`)
* DAG fan-out (`parallel`, `pipeline`)
* isolated worktrees (`isolated: true`)
* process supervision and peer coordination (`hub`)

### Does NOT Own

* planning
* governance
* project management
* Linear
* authorization (no merge authority)

OMP is equivalent to an IDE for autonomous workers, plus the primitives to
orchestrate them. guava-os composes those primitives; OMP does not decide what
runs.

---

## GitHub

GitHub owns authorization — the machine enforcement that replaces gorp's
transition table and fail-closed promotion.

### Owns

* branch protection (production, staging)
* required pull-request review
* required status checks (CI: tests, build, lint)
* the merge boundary (dev → staging → production)
* commit and PR history (the audit trail)

### Does NOT Own

* planning
* governance decisions
* project management
* Linear

---

## Linear

Linear is the canonical project backlog **and** the workflow state of record.

### Owns

* issues (the unit of work)
* issue status (Todo → In Progress → In Review → Done)
* dependencies (`blocks` / `blocked-by` — the execution DAG)
* the handoff record (issue description + comment thread)

### Does NOT Own

* authorization
* execution
* code

Only guava-os communicates with Linear. Workers never read or write Linear
directly.

---

## Workers

Workers are OMP subagents. They execute one deliverable each inside an
isolated worktree.

### Owns

* executing the task contract (the issue's Why / Scope / Acceptance)
* editing code, docs, tests, analysis
* running local verification
* committing with the `GUA-###` identifier and pushing to `dev/<role>`

### Does NOT Own

* merging to staging or production (GitHub-owned, operator/QA-gated)
* approval or promotion
* project management
* Linear access

Workers execute. Workers never merge. Workers never govern.

---

## Project Repositories

Project repositories own:

* product source code
* project architecture
* project documentation
* requirements and business context
* tests
* project conventions
* local capability specialization
* project-specific evidence

# Retired: gorp

gorp is retired (2026-08-20). Its responsibilities dissolve as follows:

| gorp owned | Now owned by |
|---|---|
| execution graph + dependency graph | Linear issues + `blocks` edges (the DAG) |
| worker dispatch (adapter seam) | OMP `task` / `eval agent()` |
| worktree isolation | OMP `isolated: true` worktrees |
| execution state + transition table | Linear status + GitHub branch protection |
| retries / recovery | OMP `hub` job control + `todo` |
| audit trail | git history + PR + CI logs |
| scope gate / command gate | scoped tickets + `verify` + QA reviewer |
| fail-closed promotion | GitHub PR review + required checks |
| hash-bound review decision | git commit SHA + PR review |

No component rebuilds gorp. No project contains a predecessor gorp runtime.

# The Workflow Loop

1. **Plan** — guava-os reads Linear, decomposes work into scoped deliverables
   (one issue = one observable outcome, one role label, tight acceptance).
2. **Write Linear** — issues created/updated with the task contract (Why /
   Scope / Out of scope / Acceptance) and `blocks` dependencies.
3. **Select ready work** — zero-indegree issues (unblocked, `Todo`, role
   label) are eligible.
4. **Dispatch workers** — guava-os fans out ready issues to OMP subagents
   (`task`/`eval agent()`), each in an isolated worktree, typed by
   `outputSchema`.
5. **Workers push** — each worker verifies, commits (`GUA-### <outcome>`), and
   pushes to `dev/<role>`.
6. **QA review** — a QA subagent (or CI) reviews the diff against acceptance
   criteria, runs tests, then approves (PR to `staging`) or rejects (comment on
   the issue, status back to In Progress).
7. **Promote to staging** — merge `dev/<role>` → `staging` (protected:
   required review + required CI checks).
8. **Promote to production** — a second, separate review gate merges `staging`
   → `production`.
9. **Refresh Linear** — move issues to `Done`; the issue comment thread is the
   handoff record.

Independent work is simultaneously eligible. The DAG (Linear `blocks`) is the
only ordering constraint; OMP runs 0-indegree work in parallel.

# Branching & Promotion Model

```
production   ← protected: PR from staging + required review + required CI
    ↑
staging      ← protected: PR from dev/* + QA review + required CI
    ↑
dev/task   dev/reviewer   ...   (one per role; workers push here)
```

- Per-role dev branches isolate concurrent workers; cross-role conflicts
  resolve at the staging merge.
- A `blocks` edge means a hard result-dependency: downstream consumes the
  upstream result. Independent work is never serialized by invented edges.
- Every commit subject carries the canonical `GUA-###` identifier so QA can
  map commits to issues and acceptance criteria.
- Two promotion gates: staging review, then production review.

# Skills

The word "skill" refers to multiple concepts. These are separated.

## 1. Global Capabilities

Reusable engineering knowledge. Examples: React, Terraform, dbt, Kubernetes.
These belong to GOS and compound across every project.

## 2. Project Knowledge

Project-specific knowledge — architecture, conventions, domain knowledge,
business rules. Lives only inside one project; never promoted automatically.

## 3. Worker Skills

Execution behaviors — implement feature, review PR, refactor, generate tests.
These belong to the execution layer and define how workers perform work.
Embodied as roles.

## 4. Runtime Skills

Environment capabilities — terminal, file editing, search, git, memory. These
belong to OMP.

---

# Roles

Roles are the seven OMP agent types: `task`, `reviewer`, `scout`, `designer`,
`sonic`, `librarian`, `security-reviewer`. They belong to the execution layer. An issue carries
exactly one role label, which selects the subagent that runs it.

Roles do not own governance, approval, or promotion — those are
operator/QA-gated via GitHub.
---

# Knowledge Flow

Knowledge flows upward: Global Capability Library → Project → Execution →
Candidate Improvement → Review → Promotion → Global Capability Library.
Nothing becomes global automatically; all promotion is governed.

---

# Execution Flow

Execution flows downward: Conversation → Plan → Linear → guava-os →
OMP subagents → dev/<role> branch → GitHub review → staging → production.
Execution never bypasses review. Workers never merge.

---

# Design Rules

Every responsibility has one owner. No duplicated ownership. No hidden
orchestration. No component reaches across architectural boundaries. Higher
layers decide; lower layers execute. Authorization is a repository concern
(GitHub), never a runtime concern. Knowledge compounds through review, never
automatically.

---

# Immediate Repository Goal

The current effort is to align the repository with this architecture: retire
gorp, replace its CLI with OMP-driven skills, center workflow state in Linear,
and enforce authorization with GitHub branching. Success means ownership is
unambiguous, documentation matches implementation, and future work proceeds
without redefining responsibilities. Any feature that violates this ADR must
first update this ADR and receive explicit approval.
