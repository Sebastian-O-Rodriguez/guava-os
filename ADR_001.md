# ADR-0001 — System Boundaries and Ownership

**Status:** Accepted

**Purpose:** Define the architectural boundaries between GOS, guava-os, gorp, OMP, Herdr, and project repositories. This document is the source of truth. When code or documentation conflicts with this ADR, this ADR wins.

---

# Why

The repository has accumulated overlapping responsibilities.

Planning, orchestration, execution, runtime, and governance have become blurred.

This ADR establishes a single ownership model.

Every component has one job.

---

# Core Principle

Separate **thinking** from **execution**.

Planning is not execution.

Governance is not execution.

Runtime is not orchestration.

Execution does not own business decisions.

---

# Component Responsibilities

## GOS

GOS is the operating model.

It defines how engineering work compounds across projects.

GOS is **not** a runtime.

### Owns

* operating model
* governance model
* capability model
* promotion model
* architectural principles

### Does NOT Own

* execution
* worker runtime
* planning implementation
* project management

---

## guava-os

guava-os is the orchestration layer.

It understands projects.

It understands planning.

It decides what should happen next.

It does not execute work.

### Owns

* project state
* planning
* task decomposition
* orchestration
* Linear integration
* governance workflow
* review workflow
* promotion workflow
* project registry
* cross-project awareness

### Does NOT Own

* execution graph
* worker lifecycle
* worktrees
* retries
* execution runtime

---

## gorp

gorp is the execution engine.

Its purpose is deterministic execution.

Nothing more.

### Owns

* execution graph
* dependency graph
* worker dispatch
* worktree isolation
* execution state
* retries
* recovery
* audit trail
* execution artifacts
* promotion gates

### Does NOT Own

* Linear
* planning
* backlog
* governance
* prioritization
* business context
* portfolio management

gorp must remain reusable regardless of task system.

Replacing Linear with another system must not require changes inside gorp.

---

## Workers

Workers execute tasks.

Workers never govern.

Workers may propose changes.

Workers never approve changes.

Outputs include:

* code
* documentation
* tests
* analysis
* capability proposals

Workers return artifacts to gorp.

---

## OMP

OMP is the engineering runtime.

It provides the environment in which workers execute.

OMP is not an orchestrator.

### Owns

* runtime
* shell
* tools
* context loading
* memory
* skills loading
* model access

### Does NOT Own

* planning
* orchestration
* governance
* project management
* Linear

OMP is equivalent to an IDE for autonomous workers.

---

## Herdr

Herdr manages multiple OMP sessions.

Each pane represents one active project runtime.

### Owns

* session management
* operator visibility
* project switching
* blocker surfacing

### Does NOT Own

* execution
* planning
* governance

---

# Linear

Linear is the canonical project backlog.

Only guava-os communicates with Linear.

The execution engine must not.

```
Conversation

↓

↓

Linear

↓

guava-os

↓

gorp

↓

Workers

↓

Artifacts

↓

guava-os Review

↓

Linear Update
```

gorp never reads or writes Linear.

# Skills

The word "skill" currently refers to multiple concepts.

These are separated.

## 1. Global Capabilities

Reusable engineering knowledge.

Examples:

* React
* Terraform
* dbt
* Kubernetes

These belong to GOS.

They compound across every project.

---

## 2. Project Knowledge

Project-specific knowledge.

Examples:

* architecture
* conventions
* domain knowledge
* business rules

Lives only inside one project.

Never promoted automatically.

---

## 3. Worker Skills

Execution behaviors.

Examples:

* implement feature
* review PR
* refactor
* generate tests

These belong to the execution layer.

They define how workers perform work.

---

## 4. Runtime Skills

Environment capabilities.

Examples:

* terminal
* file editing
* search
* git
* memory

These belong to OMP.

---

# Personas

Personas are execution policies.

Examples:

* Planner
* Backend Engineer
* Frontend Engineer
* Reviewer
* Architect
* QA

Personas belong to the execution layer.

OMP loads personas.

OMP does not define orchestration.

# Design Rules

Every responsibility has one owner.

No duplicated ownership.

No hidden orchestration.

No component reaches across architectural boundaries.

Higher layers decide.

Lower layers execute.

Execution must remain deterministic.

Governance must remain human-approved.

Knowledge compounds through review, never automatically.

---

# Immediate Repository Goal

The current effort is not to add features.

The current effort is to align the repository with this architecture.

Success means:

* ownership is unambiguous
* documentation matches implementation
* implementation follows these boundaries
* future work can proceed without redefining responsibilities

Any proposed feature that violates this ADR must first update this ADR and receive explicit approval.

# Amendment 1 — Ratified Interpretations (2026-07-30)

This amendment ratifies operator decisions that interpret the boundaries
above. It does not change the boundaries; it makes them precise.

## Decision vs enforcement

**guava-os owns decisions** (what happens next, operator-facing): planning,
task decomposition, orchestration, governance workflow (review/promotion
decisions), project registry, Linear project management.

**gorp owns enforcement** (deterministic mechanics): fail-closed gates, hash
binding, audit chain, worktree isolation, worker dispatch, execution-state
transitions.

guava-os decides; gorp enforces that the decision was made correctly and
records it. Neither layer does the other's job.

## Project management via Linear

**guava-os owns project management via Linear.** Linear is the provider;
guava-os owns the interface; agents never depend on Linear directly.

```
Agent → guava-os Skills → guava-os Tooling → Linear (provider)
```

Never `Agent → Linear MCP → Linear`. Linear-only implementation — no generic
provider abstraction; swap cost is contained at the tooling layer by
interface isolation.

## Personas

Personas are defined in guava-os (`.guava-os/personas/<name>/persona.md`) and
loaded by OMP at worker dispatch time. Personas do not own governance,
approval, or promotion — those are operator-only.

## Registry

The project registry is owned by guava-os. gorp receives the registry path as
explicit input; gorp never owns the file and has no gorp-internal default path.

## Contract document

The full ownership table, inputs, outputs, and forbidden responsibilities are
in `docs/architecture/guava-os-gorp-contract.md`. This ADR and that contract
are consistent; ADR_001 wins on conflict.
