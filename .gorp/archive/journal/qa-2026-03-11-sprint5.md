### WARN

**W2 — N+1 query pattern in getOverallStreaks (UNCHANGED from Sprint 3)**
File: `src/actions/completions.ts` lines 510-514
`getOverallStreaks` maps over active habits and calls `getStreaks(habit.id)` for each via `Promise.all`. `getStreaks` internally issues 2 Prisma queries (completions fetch + habit.frequency fetch). For N active habits this is 2N+1 round-trips per Progress page render (force-dynamic). Currently acceptable for a small personal habit list. Worth fixing if habit count grows past 10-15.
Suggested fix: consolidate into `getDashboardStats`-style single batch fetch and compute streaks inline.

**W6 — Streak values disagree between metric cards and sparkline badges (UNCHANGED from Sprint 3)**
File: `src/actions/completions.ts`
`getDashboardStats` (used by SparklineTable) computes streaks bounded to the 30-day window. `getStreaks` (used by `getOverallStreaks` for MetricCards) is unbounded — it reads the full completion history. A user with a 35-day streak will see "35" in the Current Streak metric card but only "30" (or less) in the sparkline streak badge. The inconsistency is silent and confusing.
Suggested fix: either (a) document intentional difference in code comments, or (b) extend the sparkline streak window to match `getStreaksForActiveHabits` (120-day lookback).

**W7 — toggleCompletion and completeOverdue have no try/catch wrapper (NEW)**
File: `src/actions/completions.ts` lines 41-77 and 827-859
Both mutation actions issue multiple Prisma calls without try/catch. If the database throws on `findUnique`, `delete`, or `create`, the unhandled exception will surface as an unhandled server action error. The optimistic UI in the client will not roll back automatically — it relies on the transition completing, but does not inspect the return value for errors.
In `HabitList.handleToggle` (habit-list.tsx line 102) and `handleCompleteOverdue` (line 117), the server action call is not awaited with error inspection. If the server throws, the optimistic state stays flipped while the DB is unchanged.
Suggested fix: wrap both in try/catch and return `{ error: string }` on failure. In the client components, check the return value and revert optimistic state on error.

**W8 — JSON.parse in ToolResultCard is unguarded (NEW)**
File: `src/components/chat.tsx` line 27
`const parsed = JSON.parse(result.result)` — if the tool executor ever returns malformed JSON (network truncation, model hallucination in tool args), this throws a render-blocking uncaught error in React. The component is not wrapped in an error boundary.
Suggested fix: wrap in try/catch and render an error state. Also applies to `JSON.parse(toolCall.function.arguments)` in `src/app/api/chat/route.ts` line 61 — if the model returns malformed JSON for tool args, the route throws uncaught and returns a 500.

**W9 — ESLint gate fails: unused import in habits.ts (NEW)**
File: `src/lib/habits.ts` line 1
`import type { FrequencyConfig } from "./types"` — `FrequencyConfig` is imported but never used in this file. ESLint reports this as a warning and `--max-warnings 0` causes the gate to fail.
Suggested fix: remove the unused import. The type annotation in the function signatures uses `unknown` (which is correct — the functions accept arbitrary JSON from the DB), so the import is genuinely dead.

### INFO

**I1 — No test infrastructure present (UNCHANGED)**
`vitest`, `jest`, `@testing-library/*` are absent from package.json. No test files exist. The `pnpm vitest run` gate is non-functional. Core logic in `src/lib/habits.ts` (normalizeDate, habitAppliesToDate, habitShowsOnDate, getWeekStart, streak computation) is pure and highly testable.
Suggested fix: add vitest + @testing-library/react to devDependencies and write unit tests for the habit utility functions as a minimum viable test suite.

**I2 — Prettier not installed (NEW)**
`prettier` is absent from devDependencies. The quality gate `pnpm prettier --check .` cannot run. Formatting consistency is enforced only through editor convention. This is low risk for a single-developer project.
Suggested fix: add `prettier` and a `.prettierrc` config if the gate is intended to run.

**I3 — normalizeDate uses local-time getters (UNCHANGED)**
File: `src/lib/habits.ts` lines 4-7
`normalizeDate` calls `date.getFullYear()`, `date.getMonth()`, `date.getDate()` which are local-time methods, then passes them to `Date.UTC()`. On a server running in UTC (Vercel) this is harmless. If Vercel's timezone ever changes or the code runs in a non-UTC environment, dates would shift. Low risk in practice.
Suggested fix: use `date.getUTCFullYear()`, `date.getUTCMonth()`, `date.getUTCDate()` for explicit UTC consistency.

**I4 — Dead export: getCompletionsForMonth (UNCHANGED from Sprint 3)**
File: `src/actions/completions.ts` line 103
Exported but never imported or called anywhere in the codebase. The Monthly Grid uses `getMonthlyGridData` exclusively.
Suggested fix: remove the export or add a comment marking it as an intentional utility reserve.

**I5 — Dead export: getHabit (singular) (UNCHANGED from Sprint 3)**
File: `src/actions/habits.ts` line 228
Exported but never called from any page, component, or other action. The AI chat uses `getHabits` (plural).
Suggested fix: remove.

**I6 — getOrCreateUser race condition (ACCEPT)**
File: `src/lib/user.ts` lines 7-13
`findFirst()` then `create({})` is a read-then-write without a transaction. On a true single-user app with low concurrency, this is harmless. Noting for completeness.

**I7 — Chat API has no rate limiting or request size validation (NEW)**
File: `src/app/api/chat/route.ts`
The POST handler accepts `body.messages` as-is with no maximum message count, no maximum content length, and no rate limiting. A large conversation history could inflate the OpenRouter API cost significantly. No `Content-Length` check, no `messages.length` cap.
Suggested fix: cap `messages` to the last N items (e.g., 20) before sending to the API. For a single-user personal app this is low urgency but the API key cost exposure is real.

**I8 — Frequency mode toggle buttons in DayPicker missing aria-pressed (UNCHANGED from Sprint 3)**
File: `src/components/day-picker.tsx` lines 84-98
The "Every day / Specific days / Weekly target" buttons do not set `aria-pressed`. Day toggle buttons (`aria-pressed={active}` at line 112) correctly have the attribute. The inconsistency means screen readers cannot determine which mode is active.
Suggested fix: add `aria-pressed={mode === m.key}` to the mode buttons.

**I9 — HabitList toggle buttons missing aria-pressed (UNCHANGED from Sprint 3)**
File: `src/components/habit-list.tsx` lines 229-341
The habit toggle button has no `aria-pressed` attribute. Screen readers cannot report the checked state. The `role="progressbar"` on ProgressRing is correct. This gap only affects the main interaction button.
Suggested fix: add `aria-pressed={completed}` to the habit toggle button.

**I10 — fieldSizing CSS property non-standard (NEW)**
File: `src/components/chat.tsx` line 272
`style={{ fieldSizing: "content" } as React.CSSProperties}` uses a CSS property that is not yet in all browser standards. It is used to make the textarea auto-grow. The `as React.CSSProperties` cast suppresses the TypeScript error but the property may not function in all browsers. The textarea has a `max-h-[120px]` fallback class.
Impact: textarea auto-sizing may not work in Firefox. Low severity; visual fallback exists.

**I11 — Chat drawer state is not persisted across page navigation (NEW)**
File: `src/components/chat-drawer.tsx` + `src/components/chat.tsx`
When the user navigates between pages (Today → Monthly → Progress), the ChatDrawer component remounts and the `messages` state in `Chat` resets to `[]`. The conversation is lost on every navigation. This is the documented design ("session state only") but worth flagging since it creates a jarring UX if the user switches pages mid-conversation.
Suggested fix: lift message state to a React context or localStorage, or add a note to the UI that the chat resets on navigation.

**I12 — OKLCH color values hardcoded in ProgressRing (UNCHANGED from Sprint 3)**
File: `src/components/progress-ring.tsx` lines 67-68, 119
Hardcoded `oklch(0.696 0.17 162.48)` values. Will not adapt if the CSS variable `--ring` changes. Acceptable for dark-only single-theme design.

**I13 — Hardcoded `#10b981` in TrendChart (UNCHANGED from Sprint 3)**
File: `src/components/progress/trend-chart.tsx` lines 74, 82, 90
Observable Plot runs outside CSS-variable scope (SVG). Known limitation. Acceptable.

**I14 — AppNav does not include Chat link (NEW)**
File: `src/components/app-nav.tsx` lines 6-11
The `/chat` route exists as a full page but the NAV_LINKS array does not include it. Users can only reach the chat via the floating `ChatDrawer` button. There is no visible route to `/chat` in the nav. This may be intentional (chat as an overlay-only feature) but the `/chat/page.tsx` file suggests it was also intended as a navigable page.
Suggested fix: either add "Chat" to NAV_LINKS or remove the `/chat` page route and use only the drawer.

## Security Assessment

No critical security issues found.

- All DB queries use Prisma ORM with parameterized queries. No raw SQL.
- No `dangerouslySetInnerHTML` anywhere in the codebase.
- No hardcoded secrets. `DATABASE_URL` and `OPENROUTER_API_KEY` read from `process.env`. The `.env` file is gitignored (standard Next.js setup).
- All mutating server actions validate inputs: `createHabit`/`updateHabit` use Zod discriminated union validation. `toggleCompletion`/`completeOverdue`/`deleteHabit` validate the `habitId` is a non-empty string.
- Chat API accepts user messages and passes them to OpenAI SDK. No injection risk since the SDK handles serialization. The tool executor calls server actions which have their own validation.
- Single-user model with `getOrCreateUser()` means there are no ownership checks on habit IDs. A non-issue for a private single-user app.
- The `CHAT_MODEL` is `anthropic/claude-haiku-4.5` — note this model ID may need verification against the current OpenRouter model catalog.
