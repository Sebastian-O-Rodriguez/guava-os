### Findings — WARN

**W1 — `getCompletionsForDate` and `getCompletionsForMonth` have no try/catch**
`src/actions/completions.ts` lines 71–97. Both are exported from a `"use server"` file and called by
server components. If the database throws, the error propagates uncaught to the page render. Every
other exported action uses try/catch and returns `ActionResult`. Suggested fix: wrap both in try/catch.

**W2 — N+1 query pattern in `getOverallStreaks`**
`src/actions/completions.ts` lines 373–377. `getOverallStreaks` calls `getStreaks(habit.id)` for each
habit in `Promise.all`; `getStreaks` itself issues 2 Prisma queries per habit. With N active habits
this is 2N+1 round-trips on every Progress page render (force-dynamic). Acceptable at current scale;
flagged because it degrades with history growth.

**W3 — `getCompletionsForDate` fetches full habit relation unnecessarily**
`src/actions/completions.ts` lines 71–78. `include: { habit: true }` loads the full habit row; the
Today page only reads `c.habitId`. Suggested fix: replace with `select: { habitId: true }`.

**W4 — `toggleCompletion` does not revalidate `/progress`**
`src/actions/completions.ts` lines 49–63. Toggling a completion affects streak and rate data on the
Progress page, but `revalidatePath("/progress")` is absent. No user-visible impact today (force-dynamic
always re-fetches), but a latent bug if caching is ever enabled.

**W5 — `ArchiveHabitButton` swallows action errors silently**
`src/components/settings/archive-habit-button.tsx` lines 16–23. `archiveHabit` and `updateHabit` return
`ActionResult` but the button never checks the return value. A server failure leaves the UI unchanged
with no feedback. `EditHabitDialog` correctly handles errors. Suggested fix: add local error state and
display a message on failure.

**W6 — Streak computation is window-bounded in sparklines but unbounded in metric cards**
`src/actions/completions.ts`. `getDashboardStats` computes inline streaks bounded to 30 days; `getStreaks`
(used by `getOverallStreaks`) is unbounded. A user with a streak longer than 30 days will see different
numbers in the metric card vs. the sparkline badge. Suggested fix: document the intentional cap or align
both computations.

#### revalidatePath("/monthly") in toggleCompletion — PASS

Lines 50 and 63 in src/actions/completions.ts call revalidatePath("/monthly")
in both the delete and create branches of toggleCompletion.

#### Server action error handling — PASS

getMonthlyGridData, getOverallStreaks, getDashboardStats all use try/catch and
return ActionResult<T>. Errors are console.error'd and return { success: false, error: string }.

#### Observable Plot cleanup — PASS

trend-chart.tsx useEffect returns `() => { plot.remove(); }` which correctly
removes the SVG element on re-render/unmount. The container is also cleared with
`containerRef.current.innerHTML = ""` before appending the new plot, preventing
duplicate SVG elements on prop changes.

#### Optimistic UI pattern (monthly-grid) — PASS

useOptimistic<Set<string>> tracks a set of "flipped" cell keys. The toggle
function is called inside startTransition. Server error does not corrupt
client state because setFlipped is inside the transition — React will revert
optimistic state on server failure. Pattern is correct.

#### No unused imports — PASS

All imports are consumed. In particular:

- monthly-grid.tsx: useOptimistic, useTransition, toggleCompletion, cn, MonthlyGridProps, CellStatus — all used
- trend-chart.tsx: useRef, useEffect, Plot, TrendPoint — all used
- progress/page.tsx: getOverallStreaks, getDashboardStats, MetricCardData, MetricCards, TrendChart, SparklineTable — all used

#### Type safety — PASS with note

The `as unknown as FrequencyConfig` casts in completions.ts and habits.ts are
necessary because Prisma 7 types the Json field as `JsonValue` (not the domain
type). This is the established pattern from Sprint 1 and is acceptable. No
bare `any` types found.

The tickFormat callbacks in trend-chart.tsx use `(d: unknown)` casts which is
correct — Observable Plot's type for tick formatters is loosely typed and
casting to the known runtime type is the right approach.

#### N+1 query risk — LOW

getOverallStreaks calls getStreaks() per habit, which each issues 2 DB queries
(completions + habit.frequency). For a single-user personal tool with a small
habit list (<20 habits) this is acceptable. Not flagged as a block. If the
habit list grows, this could be consolidated.

getDashboardStats does a single 2-query parallel fetch (habits + completions)
and computes everything in-process. Good pattern.

#### Input validation — PASS

toggleCompletion validates habitId is a non-empty string at line 35-37.
getMonthlyGridData and getDashboardStats receive typed number params and
validate via the try/catch boundary. MonthlyPage validates year/month bounds
(2020-2100, 1-12) at lines 22-31.

#### Dark theme consistency — PASS

All new components use CSS variables (bg-background, text-foreground,
border-border, text-muted-foreground) or zinc/emerald hardcoded values
consistent with the established Sprint 1 palette. The html element has
class="dark" in layout.tsx. No light-mode-only colors introduced.

#### 2-click UX rule — PASS

- Monthly grid: one click toggles a cell directly. No modal, no confirm.
- Progress dashboard: read-only, no interactions required.
