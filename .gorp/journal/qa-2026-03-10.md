### Issues Found

1. **[medium] `progress-ring.tsx` — layout bug in the `total === 0` branch**: The outer wrapper div lacked `position: relative`, causing the absolutely-positioned text label to float away from the ring SVG on the page. Fixed by adding `relative` to the outer container class.

2. **[medium] `completions.ts` — `getStreaks` inner while-loops had no bounded safety guard**: Two `while (!habitAppliesToDate(...))` loops used to find the previous applicable day had no iteration cap. A malformed frequency value that passes the initial object shape check but returns `false` for every day could cause an infinite loop. Fixed by adding a `safetyCount < 7` guard on each loop, and pre-computing `safetyFloor` from the normalized oldest completion date (previously used the raw Prisma date directly, which could have a non-zero time component).

3. **[low] `completions.ts` — `toggleCompletion` had no input validation**: An empty or non-string `habitId` would be passed directly to Prisma's `findUnique`. Fixed by adding the same guard pattern used consistently in the habit actions, returning `{ error: "Invalid habit id" }` early. Return type updated to union `{ completed: boolean } | { error: string }`. The sole caller in `habit-list.tsx` discards the return value so no downstream type error is introduced.

4. **[minor] `add-habit-dialog.tsx` — state type was wider than the UI**: `frequencyType` was typed as `FrequencyConfig["type"]` which includes `"custom"`, but the dialog only exposes `"daily"` and `"weekdays"`. The `handleSubmit` function silently treated `"custom"` as `"daily"`. Fixed by introducing a local `SimpleFrequencyType = "daily" | "weekdays"` type used for both the state and the options array. The `FrequencyConfig` import remains for constructing the frequency object passed to the server action.

5. **[noted, not fixed] `completions.ts` — `getCompletionsForDate` does not filter by userId**: The query returns completions for any habit on the given date, without scoping to the current user's habits. In a single-user app this is functionally harmless, but it is inconsistent with how other queries are scoped. Not fixed because it would require a schema join or subquery that is out of scope for this sprint, and there is no multi-user risk at present.

6. **[noted, not fixed] `progress-ring.tsx` — hardcoded oklch color value**: `"oklch(0.696 0.17 162.48)"` is used for the emerald green completed state instead of a CSS variable. This is a minor theming debt — the value is correct for now but would not respond to theme overrides. Left as-is to avoid scope creep; logged here for a future cleanup task.
