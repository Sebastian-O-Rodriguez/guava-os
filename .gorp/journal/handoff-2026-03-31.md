## What's in progress / broken

### CRITICAL: API architecture mismatch
The Expo app fetches data via HTTP calls to `/api/categories`, `/api/logs`, etc. But the Next.js backend only has **server actions** (not HTTP endpoints) for these. Only `/api/chat` exists as an actual route handler.

The Expo app has API route files (`app/api/*+api.ts`) that contain the ported logic, but they only run when Expo Router runs server-side (EAS Hosting or `npx expo start`). The Vercel static export does NOT serve these routes.

## What's blocked

### The fundamental problem
Expo static export on Vercel cannot run server-side API routes. Three options:

1. **EAS Hosting** — Deploy Expo with server output mode. API routes (`app/api/*+api.ts`) would actually run. This is the intended Expo solution but requires EAS Hosting setup.

2. **Add real HTTP API routes to the Next.js backend** — Create `/api/categories/route.ts`, `/api/logs/route.ts`, etc. in the `legacy-nextjs` branch, redeploy to `routineme-api.vercel.app`. The Expo frontend calls these.

3. **Use Supabase client SDK directly** — Skip the API layer entirely. Expo frontend calls Supabase PostgreSQL directly via `@supabase/supabase-js`. Requires RLS setup.

**Option 2 is fastest** — takes ~30 minutes to create the missing Next.js API routes and redeploy. Option 1 is cleanest long-term. Option 3 is the biggest architectural change.
